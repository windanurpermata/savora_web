BAB I
PENDAHULUAN

1.1 Latar Belakang

Perkembangan teknologi berbasis web saat ini telah mengubah lanskap pertukaran informasi secara signifikan. Savora Web hadir sebagai platform berbagi resep kuliner modern yang memungkinkan kontributor (Contributor) mempublikasikan kreasi kuliner mereka dan anggota (Member) untuk mencari, menandai (Bookmark), serta memberikan rating pada resep. Sebagai platform interaktif yang mengelola data pengguna, resep, dan ulasan, Savora Web menuntut fondasi keamanan yang tangguh guna menjamin kerahasiaan (Confidentiality), integritas (Integrity), dan ketersediaan (Availability) data.

Permasalahan keamanan pada aplikasi web terus meningkat seiring berkembangnya metode penyerangan. Berdasarkan daftar OWASP Top 10 terbaru, kerentanan seperti Broken Access Control (Kegagalan Kontrol Akses) dan Injection (Injeksi) tetap menduduki peringkat teratas sebagai ancaman kritis. Dalam konteks aplikasi Savora Web, kegagalan dalam pembatasan otorisasi dapat berdampak fatal, misalnya seorang Member biasa dapat memodifikasi atau menghapus resep milik Contributor lain, atau bahkan mengakses panel kontrol administratif (Admin Dashboard).

Selain masalah otorisasi, keamanan basis data memegang peranan krusial. Basis data menyimpan informasi sensitif seperti kredensial akun pengguna, alamat email, nomor telepon, serta data transaksi resep. Tanpa perlindungan terstruktur, basis data rentan terhadap serangan SQL Injection (SQLi). Serangan ini terjadi ketika data masukan pengguna yang tidak divalidasi langsung disatukan ke dalam query SQL dinamis, memungkinkan penyerang mengeksekusi perintah database yang tidak sah untuk membaca, memanipulasi, atau menghapus data. Untuk itu, data sensitif seperti nomor telepon pengguna dienkripsi menggunakan algoritma Salsa20 pada tingkat kolom basis data.

Pilar penting lainnya dalam sistem keamanan adalah Manajemen Identitas (Identity Management). Identitas pengguna harus dipastikan keabsahannya sejak proses registrasi hingga autentikasi. Tanpa pembatasan login, aplikasi rentan terhadap serangan Brute Force dan Credential Stuffing, di mana penyerang secara otomatis mencoba ribuan kombinasi password untuk meretas akun. Oleh karena itu, penerapan kebijakan kata sandi yang kuat, pembatasan jumlah percobaan login (Rate Limiting), verifikasi email, autentikasi berbasis tantangan matematika (CAPTCHA), serta Multi-Factor Authentication (MFA/2FA) berbasis TOTP menjadi hal wajib guna menjaga integritas platform Savora Web dari penyalahgunaan. Di samping itu, pencatatan aktivitas administratif melalui modul Audit Logging memungkinkan penelusuran forensik apabila terjadi insiden keamanan.

1.2 Rumusan Masalah

Berdasarkan latar belakang di atas, rumusan masalah dalam implementasi keamanan ini adalah:

  1. Bagaimana merancang sistem autentikasi multi-role yang aman dari serangan brute-force dan otomatisasi registrasi palsu pada Savora Web?
  2. Bagaimana mencegah eksploitasi celah SQL Injection dan Insecure Direct Object References (IDOR/BOLA) pada query basis data aplikasi?
  3. Bagaimana mengimplementasikan Role-Based Access Control (RBAC) dan pengamanan level administratif yang membatasi hak akses berdasarkan IP (IP Whitelisting) dan level administratif (Admin dan Super Admin)?
  4. Bagaimana mengenkripsi data sensitif pengguna (nomor telepon) menggunakan algoritma Salsa20 stream cipher tanpa ketergantungan eksternal?
  5. Bagaimana mengimplementasikan Multi-Factor Authentication (MFA) berbasis TOTP untuk akun Contributor, Admin, dan Super Admin?
  6. Bagaimana membangun sistem Audit Logging untuk mencatat riwayat aktivitas administratif penting guna keperluan forensik?

1.3 Tujuan

Tujuan yang dicapai melalui kegiatan implementasi keamanan ini adalah:

  1. Membangun modul autentikasi yang dilengkapi dengan pembatasan percobaan login (Rate Limiting 3 kali, lockout 5 menit) dan verifikasi CAPTCHA matematika.
  2. Menerapkan arsitektur data access secure query memanfaatkan Eloquent ORM berbasis parameterized query untuk menjamin imunitas terhadap SQL Injection.
  3. Membangun middleware otorisasi berbasis hak akses peran (Member, Contributor, Admin, Super Admin) dan membatasi akses khusus panel admin hanya dari alamat IP localhost tepercaya (127.0.0.1 dan ::1).
  4. Mengimplementasikan enkripsi kolom nomor telepon di basis data menggunakan algoritma Salsa20 stream cipher murni PHP tanpa extension eksternal.
  5. Mengimplementasikan autentikasi dua faktor (MFA/2FA) berbasis TOTP menggunakan aplikasi Authenticator (Google Authenticator / Microsoft Authenticator) untuk peran Contributor, Admin, dan Super Admin.
  6. Membangun modul Audit Logging yang mencatat seluruh aktivitas penting administratif (login, logout, perubahan data, blokir akun) ke tabel audit_logs untuk keperluan forensik.

BAB II
ANALISIS, PERANCANGAN DAN IMPLEMENTASI

2.1 Desain Keamanan Sistem (Autentikasi, Otorisasi)

Keamanan Savora Web dirancang menggunakan pendekatan pertahanan berlapis (defense-in-depth). Desain ini memisahkan kontrol keamanan menjadi dua fase utama, yaitu Autentikasi (pembuktian identitas) dan Otorisasi (pemberian hak akses).

A. Arsitektur Autentikasi

Alur autentikasi pada Savora Web dirancang untuk menyaring pengguna secara ketat guna menepis serangan brute force dan pendaftaran akun massal oleh bot. Fitur-fitur keamanan autentikasi yang diimplementasikan meliputi:

  • Strict Validation & Complexity: Pendaftaran akun baru mewajibkan parameter email yang unik dan password yang memenuhi standar kompleksitas minimal 8 karakter, wajib memiliki huruf besar, huruf kecil, angka, dan karakter simbol spesial.
  • CAPTCHA Matematika: Setiap formulir login dan register dilengkapi dengan CAPTCHA dinamis berbasis matematika penjumlahan angka acak (1-20) yang disimpan dalam session server untuk menghindari bypass bot otomatis.
  • Rate Limiting (Lockout): Pada controller login (LoginController.php), diimplementasikan pembatasan hingga maksimal 3 kali kegagalan autentikasi. Jika batas terlampaui, IP & Email tersebut akan dikunci (lockout) selama 300 detik (5 menit) menggunakan layanan RateLimiter bawaan Laravel.
  • Session Security: Setelah login berhasil, session di-regenerasi secara otomatis dengan perintah $request->session()->regenerate() untuk mereduksi risiko serangan Session Fixation.
  • Email Verification: User yang baru terdaftar harus memverifikasi email melalui tautan bertanda tangan kriptografis (signed URL) sebelum dapat mengakses fitur-fitur internal platform.
  • Multi-Factor Authentication (MFA/2FA): Akun Contributor, Admin, dan Super Admin dapat mengaktifkan verifikasi dua langkah berbasis TOTP. Setelah login berhasil, sistem mengarahkan pengguna ke halaman verifikasi kode 6 digit dari aplikasi Authenticator (Google Authenticator / Microsoft Authenticator). Kode diperbarui setiap 30 detik secara offline.

B. Arsitektur Otorisasi

Otorisasi diterapkan menggunakan konsep Role-Based Access Control (RBAC) dengan empat peran pengguna: Member, Contributor, Admin, dan Super Admin. Request HTTP disaring menggunakan middleware keamanan kustom:

  1. RoleMiddleware: Membatasi akses rute berdasarkan peran umum user (member atau contributor). Jika pengguna yang tidak berhak mencoba mengakses, sistem menghentikan proses dan menghasilkan respon HTTP 403 Forbidden.
  2. AdminRoleMiddleware: Membagi otorisasi administrator menjadi 2 level: Admin Biasa dan Super Admin. Rute pengelolaan sensitif seperti manajemen pengguna, kategori, dan audit log hanya diizinkan untuk tingkat Super Admin. Admin biasa mendapat akses terbatas pada konten non-sensitif.
  3. AdminIpWhitelist: Menambahkan lapisan pertahanan jaringan (network layer) dengan cara menolak seluruh permintaan ke area administratif (/admin/*) apabila alamat IP peminta tidak terdaftar dalam whitelist (127.0.0.1 dan ::1).
  4. MfaMiddleware: Memverifikasi bahwa pengguna dengan peran Contributor, Admin, atau Super Admin yang telah mengaktifkan MFA telah melewati tahap verifikasi TOTP sebelum diizinkan mengakses dashboard. Jika belum, sistem mengalihkan ke halaman verifikasi 2FA.

2.2 Secure Query

Keamanan manipulasi basis data pada Savora Web dibangun dengan mengandalkan paradigma modern dari kerangka kerja Laravel Eloquent ORM. Seluruh operasi penulisan dan pembacaan query SQL diimplementasikan tanpa merangkai string secara manual (SQL string concatenation).

A. Pencegahan SQL Injection

Secara default, Eloquent menggunakan mekanisme binding parameter PDO (PHP Data Objects). Ketika query filter pencarian resep dijalankan, input pencarian dilewatkan sebagai binding parameter: 

$query->where('judul', 'like', '%' . $request->q . '%');

Mekanisme di atas menjamin bahwa nilai dari variabel `$request->q` akan selalu diperlakukan sebagai literal string, bukan sebagai bagian dari perintah sintaksis SQL yang dapat dieksekusi, sehingga menutup celah SQL Injection secara total.

B. Pencegahan Insecure Direct Object References (IDOR / BOLA)

Kerentanan IDOR (BOLA) terjadi saat pengguna dapat memanipulasi parameter ID objek untuk mengakses atau mengubah data milik orang lain. Pada Savora Web, keamanan data resep dijamin dengan menyematkan relasi kepemilikan user (`Auth::id()`) pada setiap manipulasi data (Edit, Update, Delete): 

// Menjamin hanya pemilik resep asli yang dapat mengakses form edit
$resep = Recipe::where('user_id', Auth::id())->findOrFail($id);

Dengan menyaring query berdasarkan id pengguna yang sedang login (`user_id = Auth::id()`), penyerang yang mencoba memanggil endpoint `/chef/resep/12/edit` untuk resep yang bukan miliknya akan langsung mendapatkan respons error `404 Not Found` atau `403 Forbidden` alih-alih data resep terpublikasi/dimodifikasi.

2.3 Hak Akses Database & RBAC

Model data Savora Web mengadopsi struktur relasional yang terintegrasi. Hak akses database dipetakan ke dalam bentuk kolom role pada tabel users dengan empat nilai peran: member, contributor, admin, dan superadmin.

2.4 Enkripsi Data Sensitif dengan Salsa20

Data sensitif pengguna berupa nomor telepon (phone_number) dienkripsi pada tingkat kolom basis data menggunakan algoritma Salsa20 stream cipher yang diimplementasikan secara murni dalam PHP tanpa ketergantungan pada extension eksternal (seperti OpenSSL atau libsodium).

A. Mengapa Salsa20?

Salsa20 dipilih karena karakteristiknya sebagai stream cipher yang ringan, cepat, dan telah terbukti aman secara kriptografis. Algoritma ini dirancang oleh Daniel J. Bernstein dan merupakan basis dari keluarga ChaCha20 yang digunakan secara luas dalam protokol TLS modern. Berbeda dengan AES-CBC yang memerlukan padding dan rentan terhadap serangan padding oracle jika tidak dikonfigurasi dengan benar, Salsa20 menghasilkan keystream yang di-XOR langsung dengan plaintext, sehingga lebih sederhana dan bebas dari masalah padding.

B. Mekanisme Enkripsi

Implementasi enkripsi Salsa20 pada Savora Web mengikuti alur berikut:

  • Kunci (Key): 256-bit (32 byte) yang disimpan dalam variabel lingkungan (SALSA20_KEY di file .env) dalam format heksadesimal.
  • Nonce: 64-bit (8 byte) yang dibangkitkan secara acak-aman (random_bytes(8)) untuk setiap operasi enkripsi baru, memastikan ciphertext yang berbeda meskipun plaintext sama.
  • Penyimpanan: Ciphertext dan nonce digabungkan dengan format base64(nonce + ciphertext) dan disimpan di kolom phone_number_encrypted pada tabel users.
  • Transparansi: Proses enkripsi/dekripsi ditangani otomatis oleh Eloquent accessor dan mutator pada model User, sehingga kode di controller tetap bersih dan tidak perlu mengelola enkripsi secara manual.
// Contoh Implementasi Mutator pada User Model
public function setPhoneNumberAttribute($value): void {
    if (!empty($value)) {
        $this->attributes['phone_number_encrypted'] = Salsa20Service::encrypt($value);
    }
}

// Accessor otomatis mendekripsi saat diakses
public function getPhoneNumberAttribute(): ?string {
    return $this->phone_number_encrypted
        ? Salsa20Service::decrypt($this->phone_number_encrypted)
        : null;
}

2.5 Multi-Factor Authentication (MFA/TOTP)

Multi-Factor Authentication (MFA) diimplementasikan menggunakan algoritma Time-based One-Time Password (TOTP) sesuai standar RFC 6238. TOTP bekerja secara sepenuhnya offline — tidak membutuhkan koneksi internet atau SMS — menjadikannya solusi yang tepat bahkan untuk lingkungan pengembangan lokal (localhost).

A. Prinsip Kerja TOTP

Aplikasi Authenticator di perangkat pengguna dan server Savora Web menggunakan secret key yang sama. Setiap 30 detik, kode OTP 6 digit dibangkitkan dari kombinasi secret key dan waktu Unix saat ini (floor(time/30)), menggunakan fungsi HMAC-SHA1. Karena kedua pihak menggunakan kunci dan waktu yang sama, kode yang dihasilkan pun identik sehingga dapat diverifikasi.

B. Alur Setup dan Verifikasi

  1. Contributor/Admin membuka halaman Edit Profil dan memilih menu Setup 2FA.
  2. Server membangkitkan secret key acak (Base32) dan menampilkannya sebagai QR Code (format otpauth://).
  3. Pengguna melakukan scan QR Code menggunakan aplikasi Authenticator di HP.
  4. Pengguna memasukkan kode 6 digit pertama untuk konfirmasi — secret key disimpan terenkripsi di database.
  5. Setiap login berikutnya, setelah email dan password benar, sistem mengalihkan ke halaman verifikasi OTP. Pengguna membuka aplikasi Authenticator dan memasukkan kode 6 digit yang aktif saat itu.

C. Keamanan Tambahan

  • Replay Attack Prevention: Kode OTP yang telah digunakan tidak dapat dipakai kembali dalam periode 30 detik yang sama.
  • Window Tolerance: Server mengizinkan toleransi ±1 interval waktu (±30 detik) untuk mengakomodasi perbedaan jam kecil antara HP dan server.
  • Secret Encryption: Secret TOTP disimpan di kolom two_factor_secret dalam database, hanya dapat diakses oleh sistem dan bukan oleh Admin biasa.

2.6 Audit Logging Aktivitas Administratif

Modul Audit Logging diimplementasikan untuk mencatat riwayat perubahan dan aktivitas penting yang terjadi pada sistem Savora Web. Setiap entri log tersimpan secara otomatis ke tabel audit_logs dalam basis data.

A. Struktur Data Audit Log

KolomTipe DataKeterangan

user_idBIGINT (FK)ID pengguna yang melakukan aksi

ip_addressVARCHARAlamat IP pemohon aksi

B. Aktivitas yang Dicatat

  • Login dan logout akun (Contributor, Admin, Super Admin)
  • Perubahan data profil pengguna (termasuk nomor telepon)
  • Aktivasi dan nonaktivasi MFA
  • Pemblokiran dan pembukaan blokir akun pengguna
  • Penghapusan resep oleh Admin
  • Perubahan peran (role) pengguna oleh Super Admin

Seluruh log hanya dapat diakses oleh Super Admin melalui panel /admin/audit-logs, tidak dapat dihapus dari antarmuka, dan bersifat append-only untuk menjaga integritas rekam jejak forensik.

Super Admin memiliki akses penuh: manajemen pengguna (blokir/unblokir, ubah role), penghapusan resep, dan akses eksklusif ke panel Audit Log yang mencatat seluruh aktivitas administratif. Semua akses ke area /admin/* dibatasi hanya dari IP localhost (127.0.0.1 / ::1) melalui middleware AdminIpWhitelist.
UC9 Manajemen Newsletter & Kategori Admin, Super Admin Admin dapat mengelola kategori resep (tambah, edit, hapus) dan mengirim email newsletter kepada seluruh subscriber aktif yang terdaftar di tabel newsletter_subscribers. Pengguna publik dapat berlangganan newsletter melalui halaman depan. Setiap subscriber memiliki unsubscribe_token unik untuk berhenti berlangganan secara aman tanpa perlu login.

BAB III
PENGUJIAN DAN ANALISIS KERENTANAN

3.1 Pengujian Mitigasi Brute Force & Captcha

Pengujian dilakukan untuk memverifikasi keandalan Rate Limiter dan CAPTCHA matematika pada form login. Skenario pengujian dilakukan secara berurutan dengan hasil sebagai berikut:

Skenario Uji Input yang Diberikan Hasil yang Diharapkan Status
Login dengan CAPTCHA salah Email valid, Password valid, CAPTCHA asal Ditolak, muncul pesan kesalahan CAPTCHA, session CAPTCHA di-reset ulang. Berhasil
Melakukan percobaan login gagal sebanyak 3 kali berturut-turut Email valid, Password salah, CAPTCHA benar (3x) Pada kegagalan ke-3, sistem mengunci login dan menampilkan pesan lockout selama 5 menit. Berhasil
Mencoba login pada masa lockout (detik ke-30) Email valid, Password benar, CAPTCHA benar Akses ditolak langsung tanpa memeriksa password ke database, masa tunggu ditampilkan. Berhasil

3.2 Pengujian Otorisasi & Pencegahan Bypass Akses (BOLA/IDOR)

Pengujian otorisasi ini difokuskan pada pengujian kekuatan RoleMiddleware, AdminRoleMiddleware, MfaMiddleware, serta proteksi direct object reference.

  • Pengujian IP Whitelist Admin: Mengakses rute /admin/dashboard dari perangkat lain dalam satu jaringan lokal (IP non-127.0.0.1). Hasil menunjukkan sistem menolak akses secara instan dan melempar halaman 403 Forbidden. Akses hanya diizinkan dari mesin lokal localhost.
  • Pengujian Level Admin: Menggunakan akun Admin Biasa untuk mengakses rute manajemen pengguna (/admin/users) dan halaman audit log (/admin/audit-logs). Hasil menunjukkan sistem menolak dengan pesan "Akses khusus Super Admin" sesuai logika pada AdminRoleMiddleware.php.
  • Pengujian Bypass IDOR: Melakukan login sebagai Contributor A kemudian mengirimkan HTTP request PUT secara paksa menuju URL /contributor/resep/{id_resep_milik_contributor_b}. Hasil pengujian menunjukkan Laravel mengembalikan respon 404 Model Not Found karena query disaring ketat menggunakan scope user terkait.
  • Pengujian MFA Bypass: Mencoba mengakses /contributor/dashboard secara langsung setelah login tanpa melewati halaman verifikasi OTP (2FA aktif). Hasil menunjukkan sistem mengalihkan kembali ke halaman verifikasi OTP sesuai logika MfaMiddleware.php.

3.3 Pengujian SQL Injection

Percobaan injeksi SQL dilakukan pada kolom filter pencarian resep (`/resep?q=`). Input uji coba yang dimasukkan berupa payload SQL standar untuk membypass autentikasi atau menarik data tidak sah: 

Payload Input: ' OR '1'='1' -- 
Query Hasil Eksekusi: SELECT * FROM `recipes` WHERE `judul` LIKE '%\' OR \'1\'=\'1\' --%'

Hasil analisis menunjukkan tanda petik tunggal (`'`) otomatis di-escape oleh PDO adapter (ditandai dengan penambahan backslash `\'`). Sistem memperlakukan keseluruhan input tersebut sebagai string pencarian biasa untuk mencari judul resep yang mengandung kata ' OR '1'='1' --. Tidak ada syntax SQL tambahan yang berhasil dieksekusi, membuktikan sistem aman dari kerentanan SQL Injection.

BAB IV
PENUTUP

4.1 Kesimpulan

Berdasarkan tahapan analisis, implementasi, dan pengujian keamanan yang telah dilaksanakan pada platform Savora Web, diperoleh beberapa kesimpulan sebagai berikut:

  1. Manajemen Identitas (Identity Management) pada platform Savora Web telah berhasil ditingkatkan dengan menerapkan verifikasi CAPTCHA matematika dinamis untuk menyaring bot, serta Rate Limiter login (lockout 5 menit setelah 3 kali gagal) yang terbukti ampuh mencegah serangan brute-force.
  2. Implementasi keamanan basis data menggunakan parameterized query bawaan Eloquent ORM telah menutup celah keamanan SQL Injection secara penuh. Selain itu, pembatasan query berbasis scope kepemilikan pengguna berhasil mencegah eksploitasi celah Broken Object Level Authorization (BOLA/IDOR).
  3. Mekanisme otorisasi Role-Based Access Control (RBAC) dengan empat peran (Member, Contributor, Admin, Super Admin) dan perlindungan panel admin dengan IP Whitelisting terbukti efektif dalam membatasi area sensitif sistem agar hanya dapat diakses oleh pihak yang berwenang dari host tepercaya.
  4. Implementasi enkripsi kolom nomor telepon menggunakan algoritma Salsa20 stream cipher yang dibangun secara murni dalam PHP berhasil melindungi data sensitif pengguna di tingkat basis data. Pengujian membuktikan ciphertext bervariasi antar enkripsi meski plaintext sama, menunjukkan penggunaan nonce acak yang benar.
  5. Multi-Factor Authentication (MFA/2FA) berbasis TOTP (RFC 6238) berhasil diimplementasikan untuk akun Contributor, Admin, dan Super Admin. Sistem verifikasi kode 6 digit dari aplikasi Authenticator berfungsi penuh secara offline, termasuk di lingkungan pengembangan lokal (localhost).
  6. Modul Audit Logging berhasil mencatat seluruh aktivitas administratif penting ke dalam tabel audit_logs, menyediakan rekam jejak forensik yang dapat diakses secara eksklusif oleh Super Admin melalui panel administratif.

4.2 Saran

Meskipun sistem keamanan berlapis telah berhasil diimplementasikan, terdapat beberapa saran untuk penguatan dan pengembangan lebih lanjut di masa mendatang:

  1. Penerapan HTTPS / SSL/TLS: Saat dipindahkan ke server produksi, wajib mengaktifkan HTTPS menggunakan sertifikat SSL/TLS (misalnya Let's Encrypt) agar transmisi data antar browser dan server terenkripsi sepenuhnya, termasuk session token dan kode OTP.
  2. Enkripsi Kolom Tambahan: Mempertimbangkan enkripsi kolom sensitif tambahan seperti bio pada profil kontributor, atau riwayat komentar jika berisi konten pribadi, menggunakan Salsa20 yang telah terimplementasi.
  3. Rotasi Kunci Enkripsi: Menerapkan mekanisme rotasi periodik untuk kunci Salsa20 (SALSA20_KEY) agar keamanan data jangka panjang tetap terjaga meskipun terjadi kebocoran konfigurasi.
  4. Rate Limiting pada Verifikasi OTP: Menambahkan pembatasan percobaan pada halaman verifikasi OTP 2FA untuk mencegah serangan brute-force terhadap kode 6 digit (meskipun TOTP memiliki jendela waktu yang pendek).
  5. Notifikasi Email Login Mencurigakan: Mengirimkan notifikasi email otomatis kepada pemilik akun apabila terdeteksi aktivitas login dari IP atau lokasi yang tidak dikenal, sebagai lapisan peringatan tambahan.

A. Kode Middleware IP Whitelist (`AdminIpWhitelist.php`)

<?php

namespace App\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Symfony\Component\HttpFoundation\Response;

class AdminIpWhitelist
{
    private array $allowedIps = [
        '127.0.0.1', // localhost
        '::1',       // localhost IPv6
    ];

    public function handle(Request $request, Closure $next): Response
    {
        if (! in_array($request->ip(), $this->allowedIps)) {
            abort(403, 'Akses ditolak. IP Anda tidak diizinkan.');
        }

        return $next($request);
    }
}
